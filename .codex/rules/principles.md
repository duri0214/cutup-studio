# 設計原則

仕様、設計、実装、テスト、ドキュメント、運用のすべてで KISS、YAGNI、MECE を使い、必要な複雑さだけを扱う。

## KISS（Keep It Simple, Stupid）

要件を満たす最も単純な解を選ぶ。複雑さは必要になってから追加し、過剰な設計を先に持ち込まない。

- 最初に要件の最小集合を満たす。
- 既存の型、モジュール、標準ライブラリ、プロジェクトの仕組みを優先して再利用する。
- 1つの変更が必要な範囲に閉じるよう、責務と依存を分ける。
- 命名、I/O、エラーの扱いを一貫させ、暗黙の規約を増やさない。
- 型、`enum`、制約で表せることを、コメントや実行時の分岐だけに任せない。
- 依存クレートは必要十分なものだけにする。

## YAGNI（You Aren't Gonna Need It）

現在の Issue と受け入れ条件に必要なものだけを実装する。

- 将来必要になるかもしれないという理由だけで、trait、設定、引数、互換層、抽象化を追加しない。
- 具体的な利用例のない拡張ポイントや汎用ユーティリティを作らない。
- 今回使わないエラー種別、設定項目、データ項目を先回りして定義しない。
- 将来要件が発生したときに、現在の設計を小さく変更して対応できる余地だけを残す。

## MECE（Mutually Exclusive, Collectively Exhaustive）

要件、責務、テスト、レビュー観点を整理するときに、重複と漏れを減らす。

- まず対象範囲と分類軸を定め、同じ観点の分類を重ねない。
- 1つの責務や要件が複数の層・モジュールへ重複しないようにする。
- 受け入れ条件に対して、変更に関係する正常系、境界、失敗、外部依存を確認する。
- 網羅性を理由に、Issue と無関係な将来ケースまで追加しない。対象範囲の外側は明示的に扱わない。
- 似た処理を別の名前で増やさず、同じ責務は一つの場所に集約する。

## 避けること

- 利用例のない trait、継承相当の抽象化、汎用ユーティリティを先に作ること
- 小さな変更に対する大規模リファクタリング
- `clone`、`unwrap`、設定追加で設計上の問題を隠すこと
- マクロや複雑なメタプログラミングを、単純なコードの代わりに使うこと

## 判断基準

- この変更は要件を満たす最短経路か。
- 3か月後の自分や同僚が短時間で読めるか。
- 依存、公開 API、影響範囲を小さくできるか。
- 要件、実装、テストの間に重複や漏れがないか。
- 失敗時の挙動が明確で、戻しやすいか。
