# Rust コーディング規約

Rust の型システムと標準的な所有権モデルを活かし、読みやすく明示的なコードを書く。

## モジュールとファイル構成

- Rust 2018 以降では、ファイルに分ける名前付きモジュール `foo` は `foo.rs` に置く。子モジュールがある場合は `foo/` ディレクトリに置く。
- 新規に `foo/mod.rs` を作らない。既存の `foo/mod.rs` を変更する場合は、そのモジュールを `foo.rs` へ移行する。
- 同じモジュールに `foo.rs` と `foo/mod.rs` を併存させない。
- `#[path]` は生成コードや外部要件によって標準配置を使えない場合だけに限定し、`mod.rs` を維持するためには使わない。
- ファイル配置を移行するときは、モジュール宣言、公開可視性、`crate::...` の参照パスを維持する。

## 所有権と型

- 借用と所有権を設計に反映し、不要な `clone` や `Arc` でコンパイルエラーを隠さない。
- 値の状態や種類を表せる場合は、文字列や数値の組み合わせより `enum` や newtype を優先する。
- `Option` と `Result` を使って、値がない場合と失敗を呼び出し側へ明示する。
- 外部入力やI/O境界で `unwrap`、`expect`、`panic!` を使わない。プログラムの不変条件が壊れた場合に限り、理由が分かる `expect` を検討する。
- `unsafe` は安全性の根拠と影響範囲を説明できる場合だけ使う。

## エラーと依存

- ドメイン上の失敗は、呼び出し側が分岐できる型付きエラーとして表す。
- 外部ライブラリやOSのエラーは、必要な境界でドメインまたはアプリケーションのエラーへ変換する。
- エラー文字列だけで分岐せず、`thiserror` など既存のプロジェクト方針に沿った型を使う。
- 新しいクレートを追加する前に、標準ライブラリと既存依存で解決できないか確認する。

## 非同期処理とI/O

- DB、HTTP、ファイル、プロセス、外部サービスへのアクセスは、ドメインロジックから分離する。
- 非同期ランタイムやフレームワークの型を、ドメイン層へ不用意に持ち込まない。
- `async` は必要な境界だけに置き、同期処理を理由なく非同期化しない。

## 確認

- Rust の変更後は、リポジトリの手順に従って `cargo fmt`、`cargo test`、`cargo clippy` を実行する。
- 公開 API、エラー、所有権の変更では、利用側と境界のテストを確認する。
