# ローカル素材カタログ v1

`NEW` で選んだ素材フォルダ内に `material-catalog.sqlite` を作成し、そのフォルダを登録します。
素材本体はコピーせず、正規化した絶対ルートとルート相対パスを保存します。既存の
`material-catalog.sqlite` がある素材フォルダは `OPEN` で開きます。
SQLite は bundled 版を使うため、別途 DB サーバーを導入する必要はありません。

## データ契約

実際の DDL は `src/infra/catalog_schema.sql`、Rust の入力型は
`src/domain/valueobject/catalog.rs` にあります。SQLite の `application_id` と
`user_version = 1` で形式を識別し、未対応バージョンや別の SQLite ファイルは開きません。
JSON catalog / composition manifest の `schema_version = 1` とは別のバージョンです。

| テーブル | 保存する情報 |
| --- | --- |
| catalog | 許可した素材ルート |
| materials | 素材 ID、相対パス、SHA-256、バイト数、利用可能状態、要解析フラグ、作成・更新日時 |
| segments | 安定した区間 ID、素材 ID、開始・終了 ms、入力 SHA-256、AI 値、手動値、有効値、最新ジョブ ID、作成・更新・手動確認日時 |
| analysis_jobs | 素材 ID、入力 SHA-256、モデル、解析バージョン、実行状態、失敗理由、開始・終了日時 |
| analysis_results | ジョブと区間 ID、解析時の時間範囲・メタデータ・確度・根拠の履歴 |
| segment_attributes | 有効なタグ・役割・話者の検索用索引 |
| segment_fts | 有効な文字起こし・話者・語句・映像/音響/手動タグ・役割・メモの全文検索索引 |

区間の開始・終了は整数ミリ秒で `0 <= start_ms < end_ms`。
一素材に複数区間を持ち、同じ素材 ID と時間範囲の保存は既存区間を更新します。
明示的な区間 ID を指定した手動編集は、時間範囲を修正しても ID を保持します。
別区間と時間範囲が衝突する更新は拒否します。ID はカタログ内で安定しています。

AI メタデータと手動メタデータは別に保存します。手動値の未指定（`None`）は
AI 値を利用し、明示的な空文字・空配列は AI 値を消す操作として扱います。
再解析は手動修正を上書きしません。表示・検索・候補生成は同じ有効値を使用します。
画面では、既存区間の変更した項目だけを手動修正として保存します。

## 再走査

- 対象拡張子: mp4 / mkv / mov / avi / webm / m4v / wav / mp3 / flac / ogg / m4a / aac（大文字も可）。
- サブフォルダを含めて SHA-256 を計算します。内容変更は同じサイズ・更新日時でも検出します。
- シンボリックリンク・Windows のディレクトリ再解析ポイントは辿りません。
- 新規素材と内容変更素材だけを `needs_analysis = 1` にします。走査自体は AI を実行しません。
- 移動は「旧パスが利用不能、新パスが追加」として記録します。同一内容の別ファイルを勝手に統合しません。
- 削除・移動済みの素材、旧指紋の区間、再解析で消えた AI 専用区間は保持し、編集画面で状態を表示します。
- 利用不能・要確認の区間は GUIDE の候補から除外します。変更後の素材を確認して手動保存するか、再解析すると再利用できます。
- 元のパスに同一内容の素材を戻すと、既存 ID と区間が復帰します。
- 素材ルート自体がなくなった場合も利用不能になります。アクセス拒否・読み取り失敗・走査中の変更では DB の走査結果を更新しません。
- 走査結果の反映は一つのトランザクションです。画面は別スレッドで走査し、完了時に候補と選択をリセットします。

状態は最後に成功した走査時点のものです。素材を外部で変更した後は `RESCAN` を行ってください。
動画の長さ・コーデックの検証は行わないため、区間の妥当性は外部プレイヤーで確認します。

## 解析ジョブ契約

今の GUI は手動編集のみです。後続のローカル解析処理からは
`analysis_targets` → `start_analysis(material_id, model, version)` →
`complete_analysis(job_id, results)` または `fail_analysis(job_id, reason)` を呼びます。
モデル更新時は変更のない素材にも明示的に `start_analysis` できます。
実行中ジョブは一素材につき一つです。プロセスが中断したジョブは、呼び出し側が
`fail_analysis` で失敗として記録してから再実行します。

結果には区間、各メタデータ、0〜1 の有限な確度、根拠が必要です。
走査で入力の変更・削除が判明した実行中ジョブは `superseded` になり、結果を受け付けません。
成功時は結果・履歴・索引・ジョブ状態をまとめてコミットし、要解析フラグを解除します。
失敗・不正な結果では部分保存せず、再実行対象を残します。
再解析で区間が変わる場合、古い AI 専用区間は要確認にし、手動修正がある区間は残します。

## 検索

[SQLite FTS5 の trigram](https://www.sqlite.org/fts5.html#the_trigram_tokenizer) を使い、
3文字以上は全文検索索引、1〜2文字は部分文字列検索で日本語の短い語句も扱います。
入力は検索構文として解釈せず、文字列として検索します。
タグと役割のフィルタは有効値の索引で完全一致させます。検索順位の最適化は対象外です。

## 検証

`cargo test --all-targets` で一時フォルダと実 SQLite ファイルを使い、登録・再走査・
再起動相当の再読み込み・手動優先・検索・解析履歴・ロールバック・manifest 生成を確認します。
AI 結果は固定データで検証し、モデル・ネットワーク・動画解析には依存しません。
